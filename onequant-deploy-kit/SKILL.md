# 私有化部署 · 环境搭建与交付

## 何时用

- 用户要在自己电脑上搭建本地量化环境
- 企业要求数据不出内网，需要私有化部署
- 你要给客户交付一套能跑的量化系统
- 问「部署这套东西要准备什么」

## 核心：交付的不是软件，是「跑得起来且有人负责」

客户买私有化部署，买的是三样：
1. **能跑起来** — 他自己搭要3-5 天
2. **数据可信** — 他最怕的是跑起来了但数据是错的
3. **坏了有人管** — 数据源断了有人兜底

---

## 第 1 步：环境自检（开工前必做）

**在客户机器上先确认这五项**，任何一项不过就先解决再动手：

| 检查项 | 最低要求 | 不满足的后果 |
|---|---|---|
| Python 版本 | 3.11+ | akshare/pytdx 依赖版本冲突 |
| 内存 | ≥ 8GB（推荐 16GB） | 全市场数据 + 多策略并行会 OOM |
| 磁盘剩余 | ≥ 50GB | 日线数据 3-5 年就占 10GB+ |
| 网络 | 能访问至少 2 个数据源 | 单源必挂，见第 3 步 |
| SQLite 版本 | 3.35+ | 窗口函数支持（回测常用） |

```bash
python --version
python -c "import sqlite3; print(sqlite3.sqlite_version)"
df -h   # Linux
wmic logicaldisk get size,freespace,caption   # Windows
```

**这一步不能省。** 到客户机器上才发现内存不够，等于白跑一趟。

## 第 2 步：数据管道搭建（核心工作）

### 必须做多源冗余

**单一数据源必挂。** 这是所有 A 股数据项目的第一大坑。

```
主源：akshare（覆盖全，稳定性一般）
备源：pytdx（速度快，需装客户端）
兜底：腾讯/东财 HTTP 接口（覆盖不全但能应急）
```

**降级逻辑**：主源失败 → 自动切备源；备源也失败 → 告警 + 记录缺失日。

**关键：数据必须记录来源和状态。** 每条记录要能回答「你是从哪来的、可靠吗」。

```sql
CREATE TABLE update_meta (
    date TEXT, source TEXT, rows INTEGER,
    status TEXT, note TEXT, updated_at TIMESTAMP
);
```

这个表是后续所有排障的基础——**没有它，出问题时你不知道从哪查起**。

### 必须做完整性校验

每次更新后立即校验，不要等到回测才发现：

```sql
SELECT date, COUNT(*) FROM daily_bars
WHERE date >= DATE('now','-7 day')
GROUP BY date ORDER BY date;
```

正常每日约 3800 行。低于此 → 记录为「疑似缺失」。

### 单位归一

**A 股成交量单位是「手」，1 手 = 100 股。** 所有数据源统一到「手」存储，转换只在展示层做。

## 第 3 步：数据管道故障排查决策树

按这个顺序查，不要乱试：

```
某天数据缺失
│
├─ update_meta 有这天记录吗？
│  ├─ 无→ 脚本根本没跑，或静默失败
│  │    → 检查：接口是否返回空列表但不报错（最常见）
│  └─ 有 → 看 rows 是多少
│
├─ rows 远低于 3800？
│  ├─ 是 → 部分拉取失败
│  │    → 检查：是否用了逐只串行、是否有超时、是否需要分页
│  └─ 否 → 数据其实在，问题在查询层
│
├─ 查询层问题
│  ├─ 表里查得出但代码读不到 → 检查连接/表名
│  └─ 都正常 → 检查策略逻辑是否误判
│
└─ 补数方式
   └─ 日常增量脚本只拉最新交易日，补不了历史
      → 必须用定点补日脚本：backfill_day.py <目标日期> -n20
```

**常见根因排序**（按实测频率）：
1. 批量接口静默返回空 —— 最常见，且不报错
2. 逐只串行太慢，当日没跑完
3. 代理/DNS 拦截特定域名
4. 接口本身变更字段

## 第 4 步：桌面端交付（PySide6 优先）

如果客户要求界面，**不要用 Web 架构**。理由：

- 数据在本地，Web 架构多一层服务，纯增加故障点
- 用户自己用的工具，桌面端启动即用，维护成本低
- 避免端口冲突（Web 架构最常见的崩溃原因）

**技术选型**：Python + PySide6（Qt）+ SQLite 单文件数据库。

**交付形态**：打包成 exe，附一份 `使用说明.md`。

**打包注意**：用 PyInstaller，务必 `--onefile`，并确认把数据库文件路径做成可配置。

## 第 5 步：交付验收清单（必须逐条打勾）

交付前让客户一起过一遍，避免后续扯皮：

- [ ] 连续跑 3 天无报错
- [ ] 随机抽 3 只股票，比对行情数据与券商 App 一致（价格、成交量）
- [ ] 历史数据能查到 3 年以上
- [ ] 断网重连后能自动恢复
- [ ] 主数据源失效时能自动切备用源
- [ ] 界面能正常打开、切换、查询
- [ ] 有使用说明（包含常见问题）

**第 2 条最关键。** 客户最在意的不是功能多不多，是「数据跟我看的对不对得上」。

## 第 6 步：远程交付标准流程

```
第 1 天  沟通需求 → 确认范围与价格 → 预付 50%
第 2 天  环境自检（远程或让对方跑检查脚本）
第 3 天  数据管道搭建 + 首日验证
第 4-5天 全量数据回补 + 交叉校验
第 6 天  界面配置（如需要）+ 培训
第 7 天  客户验收 → 付尾款
```

**要点**：
- **先收预付款**。这是信任的第一步，也是筛选不靠谱客户的机制
- 环境自检让客户自己跑（给一个一键检查脚本），避免远程连不上
- 交付后留 7 天质保期，明确写在单子里

## 边界（必须写进合同/说明）

明确说不做什么：

- ❌ 不承诺策略收益率
- ❌ 不保证数据源 100% 可用（公开数据源，官方也会调整）
- ❌ 不负责客户的交易决策
- ✅ 保证数据管道可维护、故障可恢复
- ✅ 保证交付物在约定范围内可运行

**为什么要写**：避免后续「你怎么没保证我赚钱」这类纠纷。这不是推卸责任，是专业交付的标准做法。
