# Case 001 · 用资料库把量化服务报价与交付台搭成在线工作台

**日期**：2026-10-07
**类型**：交付台搭建 / 能力商品化
**耗时**：单次会话内完成

---

## 1. 真场景

用户是A 股量化独立开发者，已有一个跑通的本地量化系统（akshare + pytdx 数据管道、12 种策略、回测与模拟盘、PySide6 桌面端），但技术能力完全没有商业化。

他的原话是：

> 「我的量化比那些开源能直接用的项目垃圾多了。」

以及：

> 「别人能用 Work 这个软件，干嘛出钱修复呢？我也是用你。」

**关键判断点**：他的问题不是技术能力不足，而是**把「技术质量」误当成「商业价值」**。
他需要的第一件事不是开发工具，而是**看见自己的能力已经被明码标价**。

---

## 2. 真过程

### 输入

- 用户已有能力清单（数据管道、回测、策略、桌面端）
- 三项质疑：软件付费时代过去了 / OPC 都倒闭 / 我的东西垃圾

### 执行步骤

**第一步：把技术翻译成「客户能看到的结果」**

核心转换公式：

```
❌ 精通 pytdx 批量接口与多源降级
✅ 接口挂了自动切备用源，成交量单位统一，历史数据不再错乱
```

产出 6 项标准服务，附工时与难度：

| 服务 | 参考价 | 工时 |
|---|---|---|
| 策略有效性回测报告 | ¥1,500 | 6h |
| 数据源故障修复 | ¥2,000 | 4h |
| 每日决策辅助回放 | ¥3,000 | 10h |
| A股本地数据库搭建 | ¥5,000 | 12h |
| 私有化行情终端部署 | ¥12,000 | 30h |
| 量化环境整体代搭 | ¥20,000 | 50h |

**刻意只主推 4 项小单**，把1.2 万和 2 万的两项标为不主推——因为还没有交付案例，不该接大单。

**第二步：搭在线交付台**

用资料库「数据表 + 在线 page」，两张表：

- `接单交付台-订单`：客户 / 需求摘要 / 服务类型 / 状态 / 报价金额 / 约定交付日 / 来源渠道 / 备注
- `接单交付台-服务报价`：服务名称 / 客户能看到的结果 / 参考报价 / 预估工时 / 难度 / 交付周期 / 推荐主推

页面结构：今天要处理（逾期标红 + 一键推进）→ 四个统计 → 双Tab（订单台账 / 报价单）。

**第三步：自检**

按平台规范跑 SDK lint，确认无循环调用、字段名与 schema 完全一致、绑定标注完整。

---

## 3. 真结果

- 交付了一个在线工作台（32KB 单文件，零外链）
- 6 条服务商品 + 3 条示例订单（含1 条逾期）入库
- 数据存云端，多设备可访问
- SDK lint 全部通过（`MINDX_DBSDK_LINT_OK`）

**最重要的结果不是工具本身**，而是把用户的技术能力变成了明确的标价清单——他第一次看到「原来这些东西可以值 5000 块」。

---

## 4. 真边界

### 什么情况下这个做法不适用

- **如果没有具体能力清单**，翻译不出来。必须先能列出「我做过什么、解决了什么问题」
- **如果客户群本来就有付费习惯**（比如开发者买 Postiz），不需要这一步。散户群体特殊——他们的心理账户是「亏钱可以，工具收费不行」

### 我不知道的部分

- 6 项服务的报价是**推算的**，没有真实成交数据支撑
- 「今天要处理」的逾期提醒是否真的会被使用，要看实际跑起来的行为
- 各平台的转化率完全没验证过

### 过程中踩的坑

1. **资料库脚本 `--stdin` 模式要求 payload 是对象**（`{database_id, records}`），传数组会报「输入 JSON 为空或格式非法」，错误信息不指向真实原因
2. **写入记录时 `text` 字段必须写成 `{"text": "值"}`**，裸字符串会被判定为空记录而静默拒绝
3. `import_html.py` 的 `--file-name` **必须带 .html 后缀**，否则报「不支持的文件扩展名」
4. lint 的 DSDK002 只认 `databaseId: '字面量'` 或 `DATABASE_ID` 常量，**传变量名不通过**
5. 本机 bash 缺 coreutils（cat/sed/mkdir/date 全不可用），中文参数与管道易被吞，最终一切调用走Python subprocess

### 下次会怎么改

- **先确认能力清单再动手**，不要先搭工具
- 报价应该做成可编辑的表，而不是一次写死在文档里——真实成交后要能快速调整
- 提前把「获客渠道」也做成记录字段，而不是事后回忆

## 附：一个被纠正的认知

搭建过程中，用户提出了几个判断，逐条核对后修正如下（这部分保留，因为它本身就是最有价值的部分）：

| 用户原判断 | 核对结论 |
|---|---|
| 软件付费的时代过去了 | **部分为真**：卖软件确实死了；但「有人愿意为结果付钱」没变（Postiz $170k MRR 是 Stripe 实测快照） |
| 我的东西比开源项目垃圾 | **不成立**：代码质量与商业价值无相关性。真正决定价值的是「多少人真在用 / 他们为什么搞不定 / 他们付过多少钱」——当前状态是 1 人 / 0 元，这是分发问题不是技术问题 |
| 没人愿意把赚钱办法写出来 | **不成立**：AgentWork 社区公开了 3.3k star 的实战蓝皮书、49篇指南、31 个真实任务。稀缺的不是方法，是「跑通并愿意写出来的人」 |
| 游戏打金能赚钱 | **性价比极低**：单台日收益 25-40 元，稳定运营超1 年的只占 2%，月封号率超 20% 必亏。不如一个数据修复单 |

**可复用的核心判断**：

> 能被自动化的只有「怎么做」，不能被自动化的是「该不该这么做」和「出了事谁负责」。
> 客户付钱买的是后者。
